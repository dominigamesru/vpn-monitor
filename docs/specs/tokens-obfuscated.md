# Спека: токены в зашифрованном файле `tokens.json`

Статус: **предложение, не реализовано** (план — v0.6). После решения заказчика — ADR и реализация.

## Зачем
Сейчас токены (`CONFLUENCE_TOKEN`, `GITLAB_TOKEN`, …) лежат открытым текстом в `secrets.env` в папке установки.
Их видно при показе папки на звонке с поддержкой, в архиве папки, в бэкапе, при поиске по диску `*_TOKEN=`.
Цель — чтобы файл на диске был нечитаем без этого приложения на этой машине у этого пользователя.

## Что защищает и что нет
| Угроза | Защищает? |
|---|---|
| Файл увидели на экране, в архиве, в бэкапе | да — внутри шифротекст |
| Файл скопировали на другой компьютер или другому пользователю | да — ключ привязан к машине и пользователю |
| Поиск секретов по диску (`*_TOKEN=`, регулярки сканеров) | да |
| Программа, запущенная под этим же пользователем, или человек с доступом к машине и исходникам | **нет** — GUID вшит в exe публичного репозитория, ключ можно повторить |

Вшитый GUID — **обфускация**, а не секрет: репозиторий публичный. Настоящую защиту даёт привязка к учётной
записи Windows (DPAPI, на нём же Диспетчер учётных данных — [ADR 0006](../adr/0006-ad-login-credential-manager.md)).
Поэтому ключ строится из GUID **и** данных машины и пользователя, а слой DPAPI — опция ниже.

## Ключ
```
ikm  = BUILD_GUID (16 байт, константа в коде)
salt = MachineGuid (HKLM\SOFTWARE\Microsoft\Cryptography) ‖ SID пользователя
key  = HKDF-SHA256(ikm, salt, info = "vpn-monitor tokens v1") → 32 байта
```
- `BUILD_GUID` генерируется один раз и живёт в `src/tokens.rs`; у ключа есть короткий id — первые 8 hex GUID.
- Ротация: новый GUID добавляется в список, старые остаются **только для чтения**; при записи файл
  перешифровывается новым ключом. Так новая версия читает файлы старой, а откат на старую версию после ротации
  токены не прочитает — тогда она возьмёт их из окружения или `secrets.env` (если там остались) и напишет в логе,
  что файл новее неё.
- Опционально (вопрос заказчику): поверх — `CryptProtectData` (DPAPI, область пользователя). Тогда файл не
  расшифровать даже с исходниками без входа в Windows под этим пользователем.

## Формат файла
`tokens.json` в папке установки, UTF-8, правила совместимости — как у всех JSON проекта (поля только
добавляются, незнакомые терпятся):
```json
{
  "format": 1,
  "key": "3f9a1c2e",
  "alg": "aes-256-gcm",
  "updated_ms": 1793559237000,
  "entries": {
    "CONFLUENCE_TOKEN": { "n": "<base64 nonce 12 байт>", "c": "<base64 шифротекст+тег>" }
  }
}
```
- Каждое значение шифруется отдельно, nonce — случайный на каждую запись; имя ключа — в associated data, чтобы
  значение нельзя было переставить под другое имя.
- Незнакомый `alg` или `key` → запись пропускается, в логе «tokens.json: CONFLUENCE_TOKEN — незнакомый ключ
  3f9a…, нужна версия новее».

## Откуда берутся токены (порядок поиска)
1. Переменные окружения.
2. `tokens.json` (новое).
3. `secrets.env` — как сейчас, для совместимости.
4. Вход AD из Диспетчера учётных данных — для пользователя и пароля.

**Перенос из `secrets.env`:** при запуске токены из `secrets.env` переписываются в `tokens.json`, а в
`secrets.env` вместо значения остаётся строка `# CONFLUENCE_TOKEN перенесён в tokens.json`. Ввод нового токена —
в окне «Подключение» (поле «Токен Confluence»), `POST /api/tokens` (только `127.0.0.1` и заголовок
`X-VPN-Monitor: 1`); ответ и лог — без значения: «задано (tokens.json)».

## Реализация
- Крейты: `aes-gcm`, `hkdf` (`sha2` уже есть); DPAPI — `windows-sys` `Win32_Security_Cryptography`.
- Модуль `src/tokens.rs`: `load(dir) -> HashMap<String, String>`, `set(dir, name, value)`, `migrate_from_env_file`.
- Диагностика и лог: только «задано (tokens.json)» / «пусто», никогда значение.

## Тесты
- Запись → чтение даёт то же значение; файл не содержит значения открытым текстом.
- Другой `MachineGuid` или SID → не расшифровывается, ошибки нет, токен «пусто».
- Незнакомые поля в файле и незнакомый `alg` в записи — файл читается, остальные записи целы.
- Перенос из `secrets.env`: токен в `tokens.json`, в `secrets.env` — комментарий, остальные строки на месте.
- Ротация: файл со старым `key` читается, после записи — новый `key`.
